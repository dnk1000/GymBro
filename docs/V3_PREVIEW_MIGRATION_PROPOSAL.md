## Deliberate migration transaction

1. **Select and preserve source.** Explicitly select complete supported legacy JSON or same-account complete cloud JSON. Retain original bytes and record byte SHA-256, source schema/build, filename and selection time. A directly selected local snapshot is captured read-only, downloadable and checked again before submit; changed bytes invalidate preparation. Corrupt/future/unrepresentable content rejects without writes. Keep personal bytes and detailed diffs out of Git, public logs and CI artifacts.
2. **Validate detached candidate.** Use existing supported in-memory legacy upgrades, #16 exact-label conversion and #25 conservative notes. Compare normalized source to lossless source reconstruction. Document every representation change rather than implying schema-7 raw JSON equals schema-8 canonical rows. Exact aliases/explicit existing mappings may resolve; no fuzzy merge, guessed session, timestamp, note meaning or training equivalence. Retain old raw bytes and unknown metadata, including colliding legacy `noteScopes` content.
3. **Freeze identities.** Canonical exercise allocation follows #16 unchanged. Legacy bodyweights have no relational IDs: compute a normalized-source digest using SHA-256 over UTF-8 JSON with recursively sorted object keys and preserved array order, excluding no source fields. For ordinal `i`, hash the JSON array `["GymBro issue28 bodyweight v1", sourceDigest, i]`; take the first 16 digest bytes and set UUID version 8/variant bits. Reject collisions. This is key allocation, not date/value deduplication; identical bodyweight rows at different positions remain distinct. Preserve keys/signature schemes in cloud files; legacy guided signatures remain byte-identical with their existing interpretation scheme. These deterministic allocations are a proposed #28 choice requiring approval, not an already accepted contract.
4. **Read destination consistently.** Use #41's owner/revision/raw-fingerprint snapshot. Refuse unreadable state, unsupported versions, conflicting canonical catalog, or any different existing aggregate. An initial migration requires every workout/catalog table empty, including exercises/aliases; an uninitialized status alone is insufficient. Revision/fences are not reset. For an initialized destination, only exact equality to the **frozen canonical migration candidate**, including deterministic/preserved bodyweight keys, canonical IDs, signature schemes, all catalog fields, unknown metadata, ordering and every relationship, qualifies as already migrated. Equality is not established by source-file digest, record counts, display-equivalent content or user-visible reconstruction alone. A qualifying rerun returns a verified no-op and leaves revision/receipts untouched. Any mismatch requires review through separate existing restore/merge controls, never automatic overwrite.
5. **Review and confirm.** Display environment/account, source/schema/build, full section counts, active workout, identity mapping/separate ambiguous labels, preserved legacy content and target empty-state check. Offer the retained source/raw destination material. Require explicit final migration confirmation. Cancellation writes nothing. Missing source/gates/conflicting account/revision stops the operation.
6. **Submit once through existing boundaries.** Define a narrow `initializeMigration` lifecycle operation for verified-empty destination initialization. Reuse #41's dedicated lifecycle transaction role/capability, server-side constrained payload validation, owner lock, revision/raw-fingerprint binding and atomic delete/insert mechanics where applicable, and reuse #40's frozen operation identity, receipt-first retry/resolution and stale-response protections. Do **not** route an ordinary first-time migration through the emergency-restore UX or qualify it as emergency recovery; emergency restore remains reserved for #41's verified unreadable/uninitialized recovery case and its stronger diagnostic/raw-material confirmation contract. Enforce the migration empty-destination precondition under the server owner lock, not only in UI. A narrowly scoped new source-controlled migration may add only the initialization operation/guard needed for this boundary; do not edit applied migrations, create a second writer protocol, broaden ordinary writer permissions or create a general replacement bypass. Healthy populated replacement remains #41 complete restore with its verified-backup gate.
7. **Read back and compare.** Require acknowledged result and a fresh consistent full snapshot; verify all projected rows/reconstruction against the frozen canonical migration candidate and original-source semantics. Only then report migration verified and allow cloud workflows. A committed write with a comparison failure is reported as committed but parity failed; preserve source/destination exports and block dependent edits pending investigation. Do not falsely say nothing was saved or try an automatic rollback/reseed.

Interruption before transmission changes nothing. An uncertain transmission blocks new requests; retry the identical frozen packet or resolve/fence its operation under #40. After reload resolve the metadata-only marker first, then reselect the retained source; deterministic allocation permits exact reconstruction of the same frozen canonical candidate. A committed migration is an exact no-op on rerun only when the newly prepared canonical candidate equals the saved canonical/relational state under the full equality rule above. A cancelled/uncommitted operation can be deliberately prepared again only after terminal resolution and fresh empty-state checks. Later legitimate cloud edits make the saved state differ from the old canonical candidate; rerunning refuses replacement and preserves those edits. No migration payload or cloud workout database is automatically persisted in browser storage.
