## Proposed domain and UI contract

1. Keep `normalizeInboxPayload` and its supported `gym-tracker-chatgpt-v1` shapes, validation, generated import-ID algorithm and single-workout semantics. Resolution is a separate step after normalization; never recalculate an import ID from canonical IDs or resolution choices. Keep the normalized incoming label unchanged when mapping it. Existing trimming remains at normalization; this issue introduces no case folding, whitespace equivalence or fuzzy matching.
2. Add one DOM/storage/network-independent resolver over a **collection of normalized exercise references**, a validated canonical catalog and explicit review decisions. Each result retains its input key/position, incoming label and classification: canonical, alias, unresolved, explicitly mapped, explicitly new or explicitly skipped. Return the candidate catalog/references and summary without publishing committed state. Names and placement of helper functions are implementation discretion. Collection support is only this domain boundary; no batch envelope, batch persistence action or batch UI is included.
3. An existing canonical UUID resolves as an ID; otherwise use the existing exact alias lookup (which includes display names). Known inputs need no per-record confirmation. Report alias-to-canonical mappings. Preserve existing treatment of archived identities; do not add archive selection/restoration policy in #18.
4. Present one resolution control per distinct normalized unresolved label, applying its decision to that label's included rows. Choices: select an existing canonical exercise, explicitly create a new exercise, or skip that label's rows. Preserve existing per-set include controls and cancellation. Changing a label invalidates its old decision; changing saved state requires revalidation. Unknown, invalid, conflicting or stale mappings cannot silently become a new exercise or another target.
5. No fuzzy suggestions are necessary. Similar labels such as `Incline Smith Press` and `Smith Bench Press` remain distinct until an explicit choice. A label already assigned to another ID cannot be reassigned or merged. Any disagreement between a supplied canonical identity and explicit resolution must reject; never retarget existing historical references.
6. Explicit mapping calls `ExerciseIdentity.addAlias` with `user-created` provenance. Explicit creation calls `createExercise` with `import-created` provenance, the incoming label as display name and the existing `ensureExercise` Uncategorized/default metadata, active state and a GymBro-allocated UUID. Do not invent anatomy, equipment, equivalence or training classifications. No metadata editor is required. Repeated occurrences reuse one candidate exercise/alias.
7. Preview summary reports known canonical references, automatic aliases, unresolved labels/affected sets, approved mappings, planned new exercises and excluded sets, with the final included set count. Parsing, review, mapping, creation choice, skipping and cancellation write nothing. Skip is a deliberate visible exclusion, never an apparently successful silent subset. Require at least one included valid set under existing validation. Do not create an alias/exercise solely for excluded rows. An excluded subset retains the existing whole-workout import-ID consumption behavior; importing excluded sets later requires a deliberately distinct import, as with existing per-set selection.
8. At commit, revalidate the draft and decisions against the controller's current saved catalog, resolve all included rows, and prepare catalog additions plus the existing import candidate together. Every included row must have a valid canonical reference. Retain `{exerciseId, originalLabel}` and current field/provenance semantics. No session identity, timestamps, rich interchange or scoped setup context is inferred or added to today's sessionless Inbox records.

The accepted normal cloud route receives this workflow. Retained non-Production V2 development/regression adapters keep their name-key behavior and existing import compatibility; do not convert them into a second canonical catalog or workout authority. Manual logging/program creation, complete backup restore and history merge retain their existing contracts. Sharing helper code must not change their matching/creation behavior.

## Atomic commit, conflicts and recovery

- Reuse `commitImport` in `WorkoutCloud` and `WorkoutRepository`; replace its unknown-label auto-creation with the explicitly reviewed candidate additions. Compare/submit against the **original loaded handle**, not a fabricated base containing the new aliases. The prepared candidate may contain additions; the checked packet's base must still represent actual saved state.
- Catalog additions, sets, optional bodyweight, original-label references, import summary, revision and receipt commit atomically. Reject invalid drafts, alias collisions, duplicate import IDs or contradictory candidate relationships before publication. A database rejection rolls back everything; no separate alias-save request precedes the import.
- Same import ID never creates a second workout, bodyweight, exercise or alias. Preserve existing deterministic set-ID generation and collision validation. Import-ID tombstones remain after corrections/deletions. Existing single-workout content-hash limitations remain documented; this issue does not introduce semantic duplicate detection.
- Concurrency uses existing full-base/revision checks. A concurrent alias/catalog/import change yields conflict or explicit revalidation, never last-write-wins, auto-rebase or reassignment. Retain draft/decisions visibly for deliberate refresh and review; invalidate incompatible choices.
- Keep #40's frozen packet, owner-bound marker, same-request retry, receipt replay, cancellation fence and delayed-response guards. UUIDs are allocated only while preparing the original candidate; retry must not allocate new identities. Do not clear the visible preview on `OUTCOME_UNKNOWN`, conflict, rejection or failed save. Block editing/resubmission while a request is pending/uncertain as required by the existing controller; use its Retry/Check result controls.
- Hard reload follows the existing recovery marker contract: resolve the prior operation before new writes. No new persisted draft store, background sender, offline queue or promise of draft survival across reload is introduced. A confirmed successful result clears the preview; cancellation/failure preserves it where the existing interaction permits deliberate retry/review.
- Failure/rollback preserves all previously committed facts, receipts and inactive browser bytes. There is no schema rollback or data cleanup. Reverting code must retain the now-valid aliases and acknowledged records; old code can already resolve saved aliases. Never restore stale data as a code rollback.
