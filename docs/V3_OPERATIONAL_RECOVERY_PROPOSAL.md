## Inspected baseline and bounded implementation

The app's normal local mode remains authoritative for real workouts until accepted cutover. `?storage=cloud` is guarded synthetic Preview operation in the existing seven-view app. Workout schema **8**, identity document **1**, relational model **1**, protocol **1** and complete cloud backup format **1** remain independent of the app build. No schema, format, SQL, RPC permission or persistent-data change is proposed.

- `storage.js` already protects unreadable local bytes, notices stale tabs and refuses cloud-mode local saves. Reuse these principles; do not replace its recovery workflow or local key.
- `workout-concurrency.js` already retains frozen packets/metadata markers, blocks new writes while unresolved, protects acknowledged state and distinguishes conflict/unknown/recovery phases. It currently discards transport context in broad catches. Keep all existing phase, marker, replay and cancellation guarantees.
- `workout-repository.js` and `workout-lifecycle.js` reduce SDK errors to a generic message plus a provider code. Add only bounded diagnostic classification at these adapters as needed. A provider code or HTTP response is not automatically an acknowledgement under the checked protocol.
- `cloud-ui.js` hides workout fields before initial load and publishes only healthy snapshots, but displays raw `error.message` in several catches. Its reconnect path calls `invalidate()`, clearing drafts even for a retry by the same account. Replace raw cloud exception display and separate same-account reconnection from actual identity invalidation.
- `account-access.js` already uses generic messages and verified identities. Preserve its generation checks, token handling and local sign-out/account-change invalidation. Generic account messages need operation-aware recovery and cloud-mode wording; do not imply local workouts are available inside failed cloud mode.
- `workout-lifecycle-panel.js` already separates healthy backups from qualified raw/uninitialized/unreadable recovery and disables cleanup before cutover. It also displays raw exception messages. Preserve its confirmed restore, safety-backup and raw-material prerequisites while using the common safe presentation layer.

The expected implementation touches the common diagnostic module, these existing adapters/controller/UI modules, applicable script inclusion and focused tests, plus owning documentation/version/release checks. This is an integration in the existing runtime, not another diagnostic app. Auxiliary concurrency/lifecycle test pages may reuse the presentation helper where affected; they cannot substitute for normal-app Preview evidence. Follow [the shared UI authority](BRAND_AND_UI.md) without redesigning unrelated views.

## Failure and recovery matrix

This matrix specifies presentation and allowed deliberate actions, not new persistence states. Exact messages must state what is known, what is unknown, whether entries remain in this tab and the next safe action.

| Condition and evidence | User-facing state and deliberate recovery | Safety constraint |
| --- | --- | --- |
| Initial cloud read fails: network, timeout, database unavailable or unclassified transport failure | Saved workouts could not load; no account contents are shown. Offer retry of the read/connect and account verification when relevant. Show environment/support context. | Keep workout views unavailable. Never seed, initialize, export a successful empty backup or fall back to local data. A failed request is not a verified uninitialized account. |
| Refresh fails after a verified snapshot | Saved data could not refresh; prior displayed data is the last acknowledged snapshot. Keep entries, pause writes and offer explicit refresh. | A failed refresh must not publish an empty snapshot, discard drafts, regress a revision or overwrite an unresolved operation. |
| Network offline hint or read timeout | Explain connectivity is required; offer deliberate retry when connected. | Browser online/offline hints are advisory, not evidence that a request did or did not reach the server. No automatic background sender or offline queue. |
| Write pending or acknowledgement missing, including network/5xx/auth transport failure after transmission may have occurred | Keep #40 `PENDING` / `OUTCOME_UNKNOWN` and accurately state confirmation is pending/lost. Offer only controller-permitted same-packet retry or check-result/cancel. | Never say “not saved,” clear inputs/markers, create a fresh request key, or enable a new write based only on diagnostic classification. On hard reload the packet/draft may be gone; offer resolution rather than promising retry. |
| Definite validated application rejection | Explain the rejected operation, retain inputs and offer correction/review before resubmission. | Only existing protocol-qualified terminal rejection is definite. Do not expand rejection code ranges or treat arbitrary SQL/HTTP errors as terminal merely to show a nicer message. |
| Stale revision or reused request identity | Reuse distinct #40 conflict/request-conflict states. Explain another tab/device changed data or the original request differs. Offer refresh/review or original-result resolution as permitted. | No automatic merge/rebase/last-write-wins. Refresh saved data separately from drafts and never silently retarget an edit/session/slot. |
| Expired/invalid auth or owner verification failure | Pause access/saving and offer account refresh or fresh sign-in link. Distinguish expired link from unavailable verification and authorization denial where reliable evidence exists. | Do not guess that every permission error means session expiry. Reauthentication cannot discard an unresolved request or bypass recovery markers. Actual sign-out/owner change clears private UI state as today; do not promise its drafts survive. |
| Affirmative lifecycle snapshot reports `uninitialized` or `unreadable` | Explain the qualified state, never an ordinary empty History. Offer only existing eligible synthetic initialization or #41 raw-material/explicit recovery controls. | Network/auth/configuration/decoder failure cannot enter emergency recovery. The lifecycle boundary must positively qualify recovery; preserve all #41 validation/confirmation gates. |
| Migration not committed, uncertain, or acknowledged but readback/parity pending/failed | Distinguish validation rejection, uncertain submission and committed-but-unverified migration. Keep dependent editing blocked and offer existing same-request resolution, fresh readback/comparison or recovery guidance appropriate to that state. | Never infer complete migration from counts or receipt alone; preserve parity markers and source/report choices. Do not automatically clear markers, rerun migration with a new key, replace destination data or claim parity success. |
| Unsupported protocol/model/workout/backup schema or invalid snapshot envelope | Explain incompatibility separately from database downtime, stop dependent actions and retain source/recovery material. Offer deliberate reload of the current app or maintainer recovery guidance. | Report only observed validated version fields; distinguish supported from unknown observed versions. Do not downgrade, normalize to empty, or enter emergency restore from client decoding failure alone. App build difference alone does not reject a supported backup. |
| Recovery metadata unavailable/invalid or cannot be cleared | Keep the existing `RECOVERY_ERROR`, `RECOVERY_BLOCKED` or `RECOVERY_PENDING` message and permitted actions. Advise preserving the tab and resolving the original request. | No storage clearing/reset workaround, fabricated cancellation or success, or new writes while blocked. |

Repeated connect/load for the same still-verified account must not dispose a live unresolved controller or clear visible set/note/import drafts. Use its existing refresh/retry/resolve interfaces once connected. Before a controller exists, retry only the initial read. Preserve account-generation and response-generation guards, including owner change during an initial read. Same-owner identity continuity must be verified; an old controller must never be reused across a different account/client/project context. Reload is explicit and warns that unsaved entries/file choices may be lost; there is no promise of cross-restart draft recovery.

## Safe diagnostic contract

Construct diagnostics from an explicit primitive-field allowlist. Never spread/serialize an Error, SDK response, snapshot, request packet or arbitrary provider payload. Use fixed safe classification/message keys, bounded values and text-only rendering. Unknown provider data maps to a generic class. A hostile nested value, getter, long string or string resembling HTML must not be evaluated or become an unbounded display/export field.

The support summary may contain:

- Canonical `APP_VERSION.version`; supported workout/identity/model/protocol/backup versions and observed versions only when independently qualified. Mark unavailable/unknown values honestly.
- Validated deployment environment and public configured project reference from the existing server configuration boundary. Label normal local storage versus synthetic Preview cloud authority explicitly. Do not infer Production from a hostname or query flag; unverified configuration is **unknown/unverified**.
- Fixed operation category (account, configuration, initial load, refresh, save, migration, export/restore/merge or resolution), safe failure classification, controller phase, acknowledgement certainty and permitted recovery action labels.
- An ephemeral random diagnostic correlation UUID generated by the app, distinct from mutation identity. An actual request identifier may be included only when its provenance and constrained syntax are known safe. Guided/import request IDs are user/source-controlled strings and must not be copied just because they are called request IDs. Omit unknown identifiers; never replace the actual controller operation with a diagnostic UUID.

Exclude owner UUID/email, session/set/exercise identifiers, filenames, workout notes/facts, source text, packet arguments, tokens, keys, credentials, URL fragment/query, headers, stacks, raw provider messages/details/hints/bodies and raw database rows. Allowlist known provider codes into fixed classifications; do not echo arbitrary error-code text. Avoid network-body/console logging of any of these values. No account-wide log, analytics, remote reporting or automatic clipboard action is introduced. Offer an explicit text summary/copy action; if clipboard access fails, leave selectable safe text and explain how to copy it.

The existing raw lifecycle recovery download is **different**: it can contain sensitive owner workout data and is offered only through #41's deliberate recovery path. Label it as sensitive recovery material that the user should not share as a routine support summary. Do not remove its content needed for approved recovery, automatically attach it to diagnostics or pretend it is a validated complete backup.

## Tradeoffs and recovery

One shared classifier reduces inconsistent error text, but it is a presentation adjunct to the existing controller, not an alternate state machine. Conservative unknown outcomes occasionally require an extra explicit resolution; that protects persisted facts. An ephemeral minimal support summary gives less detail than raw errors but avoids disclosing private workouts or credentials. Separate sensitive raw recovery preserves #41's recovery capability without making ordinary support diagnostics a data export.

No runtime dependency, schema, API wire format, receipt, persisted identity or backup compatibility changes are planned. Keep accepted code/forward-repair rules for any later rollback; an app rollback cannot safely downgrade data. This preparation makes only a proposed design and documentation-map entry. Actual implementation, tests and acceptance are reported once in the PR's canonical completion report, not inferred from this plan.
