The execution contract's README, AGENTS, workflow, issue and dependency references were read, and the current Data controls, import confirmation, merge rules, canonical projection and SQL grants/guards were inspected.

Approval would decide these material points together:

1. Add a versioned complete cloud JSON format that preserves canonical and relational recovery metadata; retain supported legacy JSON and sets CSV as described below.
2. Allow an explicit complete restore to replace the entire authenticated owner's workout aggregate, including immutable history from the chosen backup, through a dedicated atomic lifecycle boundary. Preserve the live owner revision and transport receipts/fences outside that replacement.
3. Require a downloaded, reopened and content-verified backup of the exact current revision before complete cloud restore. A download click alone does not prove recovery is available.
4. Keep history merge additive under the accepted contract, with conservative canonical-identity conflicts; no fuzzy mapping or exercise merge.
5. Separate inactive local recovery cleanup from cloud operations. No browser-wide storage clearing and no local cleanup before accepted cutover.
6. **Do not support a separate cloud reset or account/data-deletion workflow in #41.** Document these as deferred; complete restore remains the supported deliberate replacement operation. No reset, Auth deletion or account cascade RPC/button is added.
7. Deliver the cloud lifecycle panel/controller on a guarded synthetic staging Preview, with explicit authority-driven wording and integration boundary. Normal local Data controls continue until #28/#29 integrate/activate the approved cloud authority; #41 does not migrate personal data or perform cutover.

Recommended release mapping: **3.12.0 for #41 alone**, subject to owner approval and rechecking intervening accepted mappings. Accepted main currently declares `3.11.2-20261030T170057Z`; [VERSION_POLICY.md](VERSION_POLICY.md) requires an explicit mapping before a deployable feature build. This proposal reserves nothing and changes neither version nor BUILD. Design/version approval is not acceptance, merge, Production, personal migration or account-fixture approval.

## Complete cloud backup and compatibility

The proposed complete cloud JSON envelope has an explicit format discriminator `gymbro-cloud-backup`, independent `formatVersion: 1`, exporting `appVersion` and a payload consisting of the validated canonical identity document, persistent bodyweight IDs and guided-signature schemes required by the repository. Include source model/identity/workout versions and source revision as provenance, never as the destination revision to restore. Export one detached, fully reconstructed consistent server snapshot, not capped table queries or a stale UI cache. Preserve order, identities, aliases/provenance, notes at every scope, zero/false/missing distinctions, sessionless history, active guidance, import identities and supported unknown metadata. No generated historical timestamps or inferred sessions.

The payload is owner-neutral: table owner UUIDs are not imported. The authenticated destination owner is supplied by the verified repository context. Do not export passwords, tokens, Auth rows, secrets, access checks or infrastructure configuration. Transport receipts/fences and the live revision counter are operational protection of the destination, not portable workout facts; they are never imported or replaced. Guided request history and import duplicate metadata **are** workout recovery data and remain in the payload. Recovery means complete supported workout content/relationships, not cloning authentication or server operational history.

Before download, validate and reproject/reassemble the payload and compare complete content/relationships, including persistent keys/signature schemes. A failed, uninitialized or unsupported cloud load cannot produce a successful empty backup. Show exported revision/time and distinguish a point-in-time backup from a continuously current dataset. Export itself performs no mutation and needs no receipt. A stale device must fetch the server snapshot for this operation.

Compatibility paths remain explicit:

| Format | Import/export contract |
| --- | --- |
| New complete cloud JSON | Primary cloud recovery format; full canonical identity and relational metadata round trip. Unknown/future format versions fail before writes, retaining original file bytes. |
| Existing complete JSON, supported schemas 1–8 | Continue validation/in-memory migration without startup writes. Explicit cloud restore may convert through the accepted identity projection, generating missing canonical/bodyweight IDs once in the frozen prepared request, never on retry. Preserve original labels/signature bytes and all supported content. No invented old sessions/timestamps. |
| Legacy JSON export | Retain a separately labelled compatibility export using the accepted source reconstruction and `createCompleteBackup` when lossless representation is possible. State that it does not contain the full canonical catalog/relational key metadata of the cloud recovery file. If a later canonical state is not representable, fail visibly rather than silently downgrade or substitute it for complete cloud recovery. |
| Sets CSV | Retain sets-only export from the loaded cloud snapshot. Never present it as a complete recovery file or accept it as complete restore. |
| Reviewed ChatGPT JSON interchange | Existing review-before-commit format and semantics remain; no provider integration or new smart import workflow. |

Use a new envelope rather than inserting reserved fields into arbitrary preserved legacy metadata. Old application builds are not promised to read the new cloud envelope; original legacy files remain usable by their supported readers. Application build mismatch alone never rejects a supported data format. Do not let an unsupported cloud envelope fall through to legacy normalization and lose fields. Malformed, PostgreSQL-unrepresentable or contradictory values fail with no writes; original bytes remain available to the user.

## Complete restore transaction and recovery prerequisite

1. Load the authenticated owner's consistent current snapshot. Resolve that controller's pending/uncertain request through #40 before allowing a new operation. The server revision check protects against other devices, including requests still in flight there.
2. Validate the selected file, supported versions, complete canonical/relational reconstruction and all relationship constraints. Generate a detached replacement candidate; do not change live state. Restore may deliberately replace an active session and immutable historical snapshots, but only as a complete confirmed dataset operation, never as an ordinary edit.
3. Obtain a complete cloud backup of the current base. Ask the user to save it, select the saved file again, and verify its reconstructed payload equals the current base including recovery metadata. Retain a proof bound to owner, revision and payload; acknowledge that app verification proves file content/readability, not long-term external storage durability. A changed owner/revision invalidates this proof. This is separate from the incoming restore file.
4. Show environment, destination account, source filename/schema/build, counts, active session and exact scope: all workout history, catalog/aliases, templates, notes, preferences and imports are replaced; account access, transport protection and local recovery files are retained. Require an explicit final confirmation. Cancelling any stage writes nothing.
5. Submit a frozen `restoreCompleteBackup` lifecycle packet through the repository/controller, including expected revision, complete base, replacement, operation identity and the verified-backup binding. Reuse #40 packet fingerprinting/receipt/resolution rules; no client service key or UI table calls.
6. Under the same owner transaction lock, check the receipt first, then current revision/full base, backup binding and candidate ownership/content/constraints. Replace only that owner's aggregate atomically. Commit all facts, one monotonically advanced revision and its terminal receipt together. Failure rolls back everything. Return an acknowledged reconstructed snapshot before showing success/clearing drafts.

Implement a new source-controlled migration and dedicated fixed-search-path lifecycle RPC with a dedicated non-login/non-BYPASSRLS role, RLS and only necessary owner-scoped DML/helper privileges. The ordinary writer retains its current permissions and immutable-intent guards. Do not disable triggers/RLS or add a client-settable bypass flag. The dedicated path deletes and reinserts the chosen owner's aggregate in FK-safe order within one transaction, validates the complete result and lets insert/relationship constraints run; it does not update historical intent through the ordinary mutation helper. Include existing canonical catalog/aliases in replacement and preserve their stable IDs from the chosen backup. Auth, diagnostic, protocol and other owners' rows are outside its table allowlist.

The lifecycle entry point must verify the complete constrained payload server-side; a browser's claim that it validated/confirmed cannot replace authorization, revision or relationship checks. The backup-binding check can enforce correspondence to the base, not prove a human saved a file; the reopened-file step is the UI recovery contract. Review the expanded delete/insert capability as an explicit architectural exception for complete restore only. Test that ordinary actions and direct browser calls cannot gain that capability.

Retain all existing transport receipts and cancellation fences across replacement; never rewind or import the live owner revision. An old committed request must replay its original result with the current snapshot without resurrecting erased facts. An old uncommitted packet must fail its stale revision/base after restore, even if the restored workout document equals an older version. A cancelled packet stays cancelled. Delayed pre-restore acknowledgements cannot regress displayed state. Restore replay follows the same rules and never repeats replacement after later workouts.

Lost acknowledgement yields `OUTCOME_UNKNOWN`. Keep the exact packet in memory for deliberate retry; the existing metadata-only session marker permits terminal resolution after reload, without storing a second workout database. Reload may lose drafts/file selection, which the UI must say accurately. Do not send a new restore key, redo ID allocation or declare failure from receipt absence. Failure to resolve leaves writes blocked and the recovery file available.

## History merge and canonical identity

Use the existing domain merge contract through the repository, adapted to canonical references without converting the authoritative store back to mutable name keys. Existing set IDs win. Add compatible sessions/ordered sets, bodyweights deduplicated by date/value and import IDs; retain current program, preferences, existing exercise definitions and durable setup. Contextual session/exercise-session notes follow history; conflicting targets reject. Retain current active pointer or adopt incoming only when none is active; two different active sessions reject. Preserve original ordering and metadata. Do not import a backup's server revision or receipts.

For a canonical cloud file, identical exercise IDs refer to the same identity; current metadata wins. New IDs may be added only with nonconflicting exact aliases. If an incoming ID or label mapping contradicts current identity, reject the entire merge and explain that explicit resolution is outside this issue. A legacy label resolves only by the accepted exact canonical/alias rule; unknown labels receive stable new identities once during preparation. No fuzzy matching or silent merge/remapping. Extend the accepted merge logic and coverage rather than adding a competing domain engine.

Validate the complete candidate before confirmation and again through server constraints. Confirmation shows additions, existing-ID handling and preserved sections. Commit one frozen checked request with expected revision/base; cancellation, validation failure or stale/conflicting state changes nothing. Conflict keeps file/mode/review choices where the browser allows; explicit refresh requires recomputing and reviewing against the new base and a new intentional operation key. Repeating the same file under a new reviewed request must not duplicate history or delete settings. No separate verified-backup gate is proposed for this additive operation; export remains available before review.

## Local recovery, cloud reset and account lifecycle

| Operation / authority | Proposed behavior and wording |
| --- | --- |
| Normal pre-cutover Data tab | Existing local backup/restore/merge/erase/seed semantics continue. Account sign-in alone does not activate cloud workouts. Do not call the active workout key an inactive recovery copy. |
| Cloud-authority Data panel | Explicit environment/account and cloud source; buttons `Export complete cloud backup`, `Restore cloud workout backup`, `Merge workout history`. Explain account access/local recovery are unaffected. No local fallback/reseeding after a failed cloud load. |
| Inactive local recovery cleanup after accepted cutover | Separate section/button `Delete this browser's local recovery copy`; explain that cloud workouts/account are unaffected and this browser copy may be needed for recovery. Export original raw bytes, reopen/verify exact bytes, then separately confirm deletion. Check accepted-cutover authority and unchanged captured raw value immediately before removing only the known legacy key. Abort if changed. Failed removal is not success. |
| Corrupt/future local recovery bytes | Preserve/download exact original bytes; never parse-normalize, seed or overwrite to permit cleanup. Do not label cloud export as a backup of those bytes. |
| Cloud reset | Explicitly deferred/not supported in this issue. Do not repoint `Erase all local data`, `Restore original seed` or local recovery cleanup to cloud writes. Complete restore is the supported replacement path. |
| Account and all-associated-data deletion | Explicitly deferred/not supported in this issue, including deletion of operational receipts and Auth identity. Sign-out is not deletion; cloud restore/cleanup does not delete the account. A later approved lifecycle design must define all retention/cascade/recovery/security obligations. No misleading deletion control or undocumented browser/admin workaround. |

Local cleanup has no authenticated RPC, no cloud mutation dependency and no `localStorage.clear()`. Keep authentication, unrelated keys and pending request markers. It must not create or save `emptyData()` in either store. Current browser storage cannot provide a cross-tab compare-and-delete transaction: restrict this control to the accepted post-cutover mode, where supported app versions no longer write the key. Old app tabs must be closed/reloaded before cleanup; broadcast/storage-event guards and the immediate byte comparison prevent supported concurrent activity. Test detected changes abort; do not claim this defeats an unsupported external writer. If a safe accepted-cutover signal is unavailable, cleanup remains disabled, not inferred from a successful login or nonempty cloud account. #29 supplies that signal under its separate approval.

## Destructive recovery rehearsal

Before personal persistence/migration testing, the existing M0 verified Production backup, expected-existing-data and physical-iPhone gates remain required; this proposal does not satisfy or waive them. #41's planned staging tests use disposable synthetic datasets only, with exact fixture/environment checks and measured cleanup. Any live fixture privilege/configuration approval required for execution must be obtained for its concrete setup; earlier #40 fixture approval is not inherited.

For each Preview restore rehearsal: export/open/verify base A; restore B after confirmation; export and compare B completely; retry the original operation after a subsequent edit and prove it cannot overwrite that edit; export current B again before recovery; restore retained A as a new explicitly reviewed operation at the current revision; compare every supported field, ID/order/relationship, bodyweight key and signature scheme. Owner revision continues forward and receipts/fences remain. Also test concurrent writes and failed validation/constraints, proving exact unchanged original state and no partial receipt/revision.

If replacement acknowledgement is lost, resolve/retry before any recovery replacement. If a restore succeeded but was the wrong choice, first export the new current dataset to preserve post-operation writes, then explicitly select the intended backup and restore at a new current revision. Recovery does not silently discard newer cloud writes. A stale backup is not automatic rollback; the summary must expose its scope and require the recovery-backup gate again. No one-click undo, point-in-time hosting guarantee, hosted reset, receipt pruning, unchecked writer or code downgrade is a recovery mechanism. Schema failures require ledger inspection and reviewed forward repair through #38.
