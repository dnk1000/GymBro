### Implemented activation and inspection contract

The explicit app route is `/?storage=cloud&rehearsal=production`. Normal URLs and `?storage=cloud` keep their existing local/staging behavior. `/api/cutover-config` defaults off; it requires `GYMBRO_CUTOVER_REHEARSAL=true`, `GYMBRO_CLOUD_ENV=production-rehearsal`, the exact approved Production ref/URL/publishable key, and Vercel's platform-provided Preview environment, branch, immutable `VERCEL_URL` and full `VERCEL_GIT_COMMIT_SHA`. The served canonical build is read from `app-version.js`, not duplicated in a second version source. A Host header for a mutable alias is refused.

To avoid the circular requirement of knowing a generated immutable URL before deploying, the operational approval is recorded **after deployment** in the existing GitHub issue #84 body. A single JSON object between `<!-- gymbro-cutover-approval-v1 -->` and `<!-- /gymbro-cutover-approval-v1 -->` supplies `version:1`, `issue:84`, `enabled:true`, `deploymentUrl`, `gitSha`, `build`, `branch`, `projectRef`, `mode`, `allowedOwners`, `actions` and `expiresAt`. Synthetic mode also requires a `gymbro-issue84-…` fixture tag; personal mode requires exactly one owner and the approved selected file's SHA-256 `sourceByteDigest`. Publish only the necessary identifiers/hashes, never credentials, emails or workout/file contents. **No such operational approval record has been populated by this implementation.** Add/change it only after the owner's specific live-operation approval; design approval is insufficient.

The server reads only that fixed repository/issue through GitHub's public API, with timeout/no redirect/no cache and no new credential. It checks the approval against trusted platform metadata and the canonical build; client-supplied identity claims cannot enable it. The browser verifies the immutable origin/build and approval digest before every Supabase Auth/RPC request, including retries/resolution, and checks the allowed action before transmission. Source-file operations recheck the approval and personal byte digest; synthetic files retain tag enforcement. RLS and existing checked RPCs remain the data authorization boundary. Unavailable/revoked/expired/mismatched approval pauses cloud controls while retaining drafts and committed state. API rate limits or GitHub unavailability also fail closed; no cached/offline approval or fallback is provided. This bounded rehearsal requires connectivity to both services and is not the future normal Production authority path.

`scripts/cutover-readiness.cjs manifest` produces a clean-commit source/hash manifest without contacting a hosted service. `list`, `plan` and `inspect` require an explicit operator session, a clean exact reviewed SHA in `GYMBRO_CUTOVER_READINESS_REVISION` and separately authorized read-only execution via `GYMBRO_CUTOVER_PRODUCTION_READ_APPROVED=true`. The target is hard-pinned; arbitrary flags, CI/Vercel invocation and apply/reset/seed/delete actions are refused. CLI output is retained only in ignored `test-results/issue84-*.json`, not printed. `supabase/inspect-cutover.sql` selects metadata only and handles absent application objects; table/column ACLs, RLS, constraints, policies, triggers, indexes, function definitions/ACLs and writer roles are compared with the disposable replay. Ledger contents are separately captured by `list`; PostgreSQL version and any documented provider differences need explicit review, not silent normalization. This tool supplies no Production apply path; any later approved promotion uses #38's separately reviewed explicit operator procedure.

## Recovery procedure and the code-rollback boundary

**Before the authority switch:** stop the rehearsal, resolve any uncertain mutation using the same frozen request or terminal resolver/fence, export/reopen the latest valid cloud backup and preserve diagnostic/raw recovery material if loading fails. Disable the rehearsal capability; verify the normal Production URL still uses its unchanged local authority. Do not delete personal cloud candidates or copy their changes over local history. If rehearsal made intentional cloud-only changes, retain and explicitly reconcile them before any later cutover. Schema changes remain; code rollback does not undo them. Use forward repair and separately approved restore if needed.

**During a later Phase 2 switch, before any cloud-only writes:** freeze writes, close/reload old app tabs/devices, inspect receipts/revisions and compare both complete datasets with the recorded cutover baseline. A code/configuration rollback can reselect the retained local authority only after proving there are no new or uncertain cloud commits and the local baseline is still current. Retain backups and the applied schema. Absence of a visible row or client acknowledgement is not proof that no write committed.

**Once any cloud-only write may have committed:** reverting app code alone is insufficient. Keep clients from writing in either mode while investigating; do not resume local logging against the stale retained copy. Resolve uncertain requests, capture a consistent current cloud backup plus raw diagnostics if reconstruction fails, record the current revision/receipts/fences and preserve the old local backup separately. Prefer a forward code/configuration repair that restores the existing cloud boundary. If data replacement is necessary, first preserve all newer facts, review the exact replacement with the owner, then use #41's same-account confirmed restore at the current qualified revision/fingerprint. Revisions advance; receipts/fences are not rewound or imported. Reopen/export/compare the full result and verify signed reload/second-context behavior before reopening writes. Use the server-qualified emergency flow only for its approved unreadable/uninitialized case, never for an ordinary network/auth failure.

A return to local authority after cloud-only writes requires a separately approved lossless reverse/reconciliation plan covering canonical metadata, all facts/relationships and compatibility, followed by verified complete comparison. Existing legacy JSON export alone does not establish that plan. If recovery files or the latest cloud state cannot be verified, remain NO-GO/write-blocked, retain originals and obtain operator/owner recovery direction. Do not reset hosted data, prune receipts, delete/reseed, disable RLS or silently drop newer records. Exact runtime writer-freeze enforcement belongs to Phase 2; documenting its required behavior here does not implement that issue.
